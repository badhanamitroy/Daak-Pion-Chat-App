## 3. Mandatory Cryptography Safety Check

The following 14 questions address cryptographic safety requirements:

### 1. How are old CBC messages identified?
In `CryptoService::decryptMessage()`, the ciphertext format is checked. If the payload does **not** begin with the version prefix `v2:gcm:`, it is routed to legacy CBC decryption:
* If the payload contains a colon (`:`), it is parsed as `<base64(iv)>:<ciphertext>` (random-IV CBC from Phase 1).
* If no colon is present, it is parsed as raw `<ciphertext>` using the original static 16-zero-byte IV (`str_repeat("\0", 16)`).

### 2. How are new GCM messages identified?
All new messages encrypted via `CryptoService::encryptMessage()` strictly prepend the version identifier `v2:gcm:`. The full serialized format is:
`v2:gcm:<base64(12-byte IV)>:<base64(16-byte Tag)>:<base64(Ciphertext)>`

### 3. Where is the nonce stored?
The 12-byte cryptographically secure random nonce (`random_bytes(12)`) is base64-encoded and stored as the 3rd colon-delimited token (`$parts[2]`) within the `message` column of the `messages` table.

### 4. Where is the authentication tag stored?
The 16-byte Galois/Counter Mode authentication tag generated by OpenSSL during encryption is base64-encoded and stored as the 4th colon-delimited token (`$parts[3]`) within the `message` column of the `messages` table.

### 5. How is authentication verified?
OpenSSL's native `openssl_decrypt()` is invoked with cipher algorithm `aes-256-gcm`, passing the extracted `$tag` as the 6th argument. OpenSSL validates the authentication tag against the ciphertext and nonce using Galois field multiplication before releasing decrypted plaintext.

### 6. What happens if authentication fails?
If ciphertext, authentication tag, or nonce has been altered or bit-flipped, `openssl_decrypt()` fails and returns `false`. `CryptoService::decryptMessage()` detects this failure, catches any decryption faults, and returns `null` (fail-closed). At the application layer (`php/get_messages.php`), any message whose decryption returns `null` is rendered as `[message unavailable]`. Attacker-controlled plaintext is never displayed and raw cryptographic exceptions are never surfaced.

### 7. Can an old CBC message still be read?
Yes. `CryptoService::decryptMessage()` retains safe read-only fallback logic for both random-IV CBC messages and initial static-IV CBC messages. Comprehensive automated tests in `tests/Phase2RemediationTest.php` verify that legacy CBC messages decrypt to their exact plaintext.

### 8. Can new code accidentally create CBC ciphertext?
No. `php/send_message.php` delegates all encryption exclusively to `CryptoService::encryptMessage()`, which contains no CBC code paths and exclusively executes `openssl_encrypt(..., 'aes-256-gcm', ...)`. Legacy CBC encryption has been deprecated and removed from write operations.

### 9. How are encryption keys loaded?
The encryption key is derived via `CryptoService::getMessageKey()`:
* If `defined('SECURITY_KEY') && !empty(SECURITY_KEY)`, it computes `hash('sha256', SECURITY_KEY, true)`, yielding a deterministic 32-byte binary key.
* Otherwise, if `app_config.php` defines `$encryption_key`, it similarly derives a 32-byte binary key via `hash('sha256', $encryption_key, true)`.
* If neither secret is configured, it fails closed by throwing a `\RuntimeException("Message encryption key is not configured.")`.

### 10. Is any key material logged?
No. The codebase was audited; neither `error_log()`, diagnostic outputs, nor exception handlers log the encryption key or binary key derivation.

### 11. Is plaintext logged?
No. Neither `php/send_message.php`, `php/get_messages.php`, nor `CryptoService.php` log plaintext message contents. When database or system errors occur, only generic operation identifiers and database error codes are written to server logs.

### 12. What is the rollback strategy?
Because legacy CBC messages remain untouched in the database and new messages use a prefixed format (`v2:gcm:...`), rolling back code to Phase 1 simply requires:
1. `git checkout security-remediation-phase1`
2. Messages created during Phase 2 will not decrypt in Phase 1 (failing safely to `[message unavailable]` or fallback), but all pre-existing CBC messages remain intact.

### 13. What happens if migration partially fails?
No bulk in-place database update was performed; encryption migration occurs organically upon new message creation. Because read-time decryption dynamically handles both `v2:gcm:` and legacy CBC payloads, there is zero risk of partial migration corruption or orphaned chat threads.

### 14. How will legacy CBC eventually be retired?
Once all conversations have aged past the organization's retention policy (or after an offline, verified CLI migration utility translates historic records), the legacy branch in `CryptoService::decryptMessage()` can be safely removed by deleting the fallback parsing lines.

### B. DP-VULN-06: Query Resource Limits & Cursor Pagination
* **Affected Files:**
  * [`php/get_messages.php`](file:///c:/xampp/htdocs/Daakpion/php/get_messages.php)
  * [`php/friendlist.php`](file:///c:/xampp/htdocs/Daakpion/php/friendlist.php)
  * [`php/chatboard.php`](file:///c:/xampp/htdocs/Daakpion/php/chatboard.php)
* **Changes:**
  * In `get_messages.php`, clamped `$limit` between 1 and 100 (default: 50).
  * Added cursor-based pagination parameters:
    * `since_id > 0`: Polling query (`AND id > ? ORDER BY id ASC LIMIT ?`).
    * `before_id > 0`: History scroll query (`AND id < ? ORDER BY id DESC LIMIT ?`, chronologically reversed).
    * Initial load: Latest 50 messages (`ORDER BY id DESC LIMIT ?`, chronologically reversed).
  * Enforced `LIMIT 100` in `friendlist.php` all-users directory query.
  * Enforced `LIMIT 100` in `chatboard.php` active friends query.

### C. DP-VULN-07: Explicit Environment Model & Secret Protection

### D. DP-VULN-08: Content Security Policy (CSP)
* **Affected Files:**
  * [`.htaccess`](file:///c:/xampp/htdocs/Daakpion/.htaccess)
  * [`php/bootstrap_security.php`](file:///c:/xampp/htdocs/Daakpion/php/bootstrap_security.php)
* **Changes:**
  * Deployed enforced CSP via Apache `mod_headers` in `.htaccess` and programmatically via `header()` in `bootstrap_security.php`:
    ```http
    Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://fonts.googleapis.com; font-src 'self' https://cdnjs.cloudflare.com https://fonts.gstatic.com; img-src 'self' data: blob:; connect-src 'self'; object-src 'none'; frame-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self';
    ```
  * Restricted `object-src 'none'` (blocks Flash/Java/plugins).
  * Restricted `frame-src 'none'` (blocks malicious embedded frames).
  * Restricted `frame-ancestors 'self'` (clickjacking prevention).
  * Restricted `base-uri 'self'` (blocks `<base>` tag injection).
  * Restricted `form-action 'self'` (blocks form hijacking).
  * Strictly omitted `unsafe-eval` to prevent dynamic script evaluation vulnerabilities.

## 7. Deployment Requirements

1. **PHP Environment:**
   * Requires PHP 8.0+ with `openssl`, `mbstring`, and `mysqli` extensions enabled.
   * `openssl_encrypt()` and `openssl_decrypt()` must support the cipher `aes-256-gcm`.
2. **Environment Variable Configuration:**
   * Production environments should configure `APP_ENV=production` in the server environment (e.g. Apache `SetEnv APP_ENV production`, system environment, or `.env` file).
   * If unset, the application automatically defaults to `production` (fail-closed).
3. **Web Server Configuration:**
   * Apache requires `mod_headers` to emit `.htaccess` security headers. If `mod_headers` is absent, the fallback in `php/bootstrap_security.php` applies to PHP responses.
   * Ensure `AllowOverride All` is permitted on the application directory.
4. **Database Migration:**
   * No schema migration or destructive database update is required. Existing message columns accommodate the `v2:gcm:...` format.

   ```bash
   httpd -k restart
   ```

## 9. Remaining Known Limitations

1. **CSP `'unsafe-inline'`:** Inline event handlers (`onclick`) in legacy HTML templates currently require `'unsafe-inline'`. Future work should extract inline event listeners to external JavaScript files to allow nonce-based or hash-based CSP.
2. **Infinite Scroll Frontend UI:** While `get_messages.php` supports `before_id` cursor pagination for historical message loading, the legacy frontend UI currently polls via interval. Adding a scroll-up backfill UI listener in `chatboard.php` will fully leverage the backend pagination capabilities.
3. **Legacy CBC Messages in Storage:** Legacy CBC messages will remain in storage until deleted or archived. They decrypt securely and fail-closed if corrupted.
